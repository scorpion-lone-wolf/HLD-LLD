# Curated Resources

These are **backup references**, not the curriculum.

Use them after an attempt or when a concept needs another explanation.

---

## Software HLD / distributed systems

### Interview-oriented
- Alex Xu — *System Design Interview*, Vol. 1 & 2
- ByteByteGo — system-design explanations and visual case studies

### Engineering depth
- Martin Kleppmann — *Designing Data-Intensive Applications*
- vendor engineering blogs for real production trade-offs
- database/storage documentation when studying implementation details

Use DDIA to deepen reasoning, not to memorize interview scripts.

---

## LLD / OOD / design patterns

- Refactoring.Guru — design-pattern reference
- small open-source TypeScript projects — existing-codebase extension/refactor practice
- unit-testing documentation for the chosen TypeScript test runner

Patterns should be learned through problems, not memorized as definitions only.

---

## India-oriented system-design preparation

Useful supplemental sources can include:
- Gaurav Sen / InterviewReady-style system-design material
- Arpit Bhayani / engineering-depth material
- candidate interview reports and community repositories

Treat candidate reports as directional signals, not official company guarantees.

---

## ML System Design

Use resources that cover the **whole system**, not only model training:

- product framing;
- labels/data;
- metrics;
- training;
- serving;
- experimentation;
- monitoring/drift.

Good reference categories:
- ML system design interview books/courses;
- production ML engineering texts;
- ranking/recommendation/search papers and engineering blogs;
- feature-store/model-serving platform documentation.

---

## GenAI / LLM System Design

Prefer current primary documentation and engineering sources for:
- model API behavior;
- context/token limits;
- structured output/tool use;
- embedding/retrieval behavior;
- fine-tuning;
- evaluation;
- safety;
- inference serving.

Model/provider details change quickly. Verify current documentation rather than relying on old memorized limits or prices.

For architecture learning, focus on stable principles:
- approach selection;
- retrieval quality;
- evaluation;
- permissions;
- failure handling;
- inference latency/cost;
- observability.

---

## Practice rule

Use external solutions only after the learner has attempted the problem.

A useful loop:

```text
attempt
→ identify gap
→ read targeted reference
→ redo from memory
→ solve a different transfer problem
```

Reading more solutions is not a substitute for unfamiliar mocks.
